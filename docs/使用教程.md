# dshenv 使用教程

`dshenv`（项目名 `dsh-envctl`）用于以声明式清单管理 DeepSeek Harness（DSH）的 Profile 插件。它会比较“清单中的期望状态”和“Profile 中的实际状态”，生成计划，并在当前支持范围内调用 DSH CLI 完成安装或更新。

> 当前能力边界：真实环境变更支持插件的 `install`、`update`、`enable`、`disable` 和受管 `remove`。`enable`/`disable` 只改 Profile `package.json` 的 `dsh.profile.bundles`，禁用后依赖仍保留。`dshenv remove` 先删清单声明；随后 `apply --yes` 只会卸载 `state.ownership` 中的插件。没有所有权的实际插件变为 `unmanaged`，不会被删除。当前没有 `purge` 命令。

## 3. 选择 DSH 环境目录

DSH 主目录按以下优先级解析：

1. 全局参数 `--dsh-home <path>`
2. 环境变量 `DSH_HOME`
3. 当前用户主目录下的 `~/.dsh`

因此，默认行为是管理当前用户的 `~/.dsh`。建议在首次试用时显式设置一个独立目录：

```bash
export DSH_HOME=/Users/costalong/code/dsh/dsh-demo
```

也可以只对单条命令指定目录：

```bash
dshenv --dsh-home /Users/costalong/code/dsh/dsh-demo status
```

相对路径会相对于当前工作目录解析为绝对路径。初始化后，主要文件位于：

```text
$DSH_HOME/
├── profiles/                 # DSH Profile 实际安装状态
└── envctl/
    ├── manifest.yaml         # 期望状态
    ├── lock.json             # 已解析的确定版本或源码
    ├── state.json            # 最近应用状态和所有权
    ├── backups/              # apply 前的管理文件快照
    └── logs/journal.jsonl    # apply 操作日志
```

## 4. 完整示例：安装 agent-teams

下面的示例把 `@nanmicoder/dsh-agent-teams@0.1.21` 声明并安装到 `web` Profile。

### 4.1 初始化

```bash
export DSH_HOME=/Users/costalong/code/dsh/dsh-demo
dshenv init
```

`init` 会创建空的 `manifest.yaml`、`lock.json` 和 `state.json`。它是一次性初始化命令：目标文件已经存在时会以退出码 `3` 拒绝覆盖。

### 4.2 声明插件

```bash
dshenv install @nanmicoder/dsh-agent-teams@0.1.21 --profile web
```

这里的 `install` 是声明式命令：它把插件写入清单，并不会立即修改 `web` Profile。生成的核心清单如下：

```yaml
apiVersion: dshenv/v1
profiles:
  web:
    plugins:
      agent-teams:
        package: "@nanmicoder/dsh-agent-teams"
        enabled: true
        source:
          type: npm
          version: 0.1.21
```

### 4.3 检查 DSH 运行时

如果使用本地 Harness 源码：

```bash
dshenv \
  --harness-source /Users/costalong/code/dsh/deepseek-harness \
  doctor
```

### 4.4 查看计划

```bash
dshenv plan
```

首次执行通常会显示一个 `install` 操作，并返回退出码 `2`，表示存在可执行的漂移，不表示命令崩溃。

### 4.5 先进行 dry-run

```bash
dshenv \
  --harness-source /Users/costalong/code/dsh/deepseek-harness \
  apply --dry-run
```

`--dry-run` 只显示计划，不获取环境写锁，也不写入状态或 Profile。

### 4.6 正式应用

```bash
dshenv \
  --harness-source /Users/costalong/code/dsh/deepseek-harness \
  apply --yes
```

当前适配器会为 `install/update` 调用等价的 DSH 插件添加操作，并把解析出的 `DSH_HOME` 传给 DSH 子进程。`enable`/`disable` 按官方公开 Profile 表示改 `dsh.profile.bundles`（关闭保留 dependencies），不调用 live manager。执行后会重新盘点实际 Profile；只有环境已经收敛，才会提交成功状态。

非 dry-run 的 `apply` 必须带 `--yes`，否则退出码 `3` 并拒绝执行。没有交互确认提示；请先运行 `plan` 或 `apply --dry-run` 审阅计划。

### 4.7 验证结果

```bash
dshenv status
dshenv plan
```

成功收敛后，`status` 显示 `healthy`，`plan` 显示没有待执行操作，两者返回退出码 `0`。

如果在仓库内使用演示目标，可以运行：

```bash

make demo-plan DEMO_HOME=/Users/costalong/code/dsh/dsh-demo
make demo-doctor DEMO_HOME=/Users/costalong/code/dsh/dsh-demo
```

其中 `demo-apply` 固定执行 dry-run。`demo-status` 已把退出码 `2` 视为“发现漂移”的正常检查结果。`demo-doctor` 默认使用 `HARNESS_SOURCE=/Users/costalong/code/dsh/deepseek-harness` 探测源码 DSH。`demo-capture` 把候选清单打印到标准输出，不覆盖 `envctl/manifest.yaml`。

## 5. DSH CLI 的解析优先级

需要调用或探测 DSH 时，`dshenv` 按以下顺序选择命令：

1. 环境变量 `DSH_CLI`
2. 命令行 `--harness-source <绝对路径>`
3. `manifest.yaml` 中的 `environment.harness.sourceDir`
4. `PATH` 中的 `dsh`

本地 Harness 源码会被转换为：

```bash
pnpm --dir /path/to/deepseek-harness dsh
```

也可以将源码目录写入清单：

```yaml
apiVersion: dshenv/v1
environment:
  harness:
    sourceDir: /Users/costalong/code/dsh/deepseek-harness
    allowUntestedVersion: false
profiles: {}
```

`DSH_CLI` 可以是单个可执行文件，也可以是 JSON 字符串数组：

```bash
export DSH_CLI=/absolute/path/to/dsh

# 带固定参数时使用 JSON 数组；命令不会交给 shell 展开。
export DSH_CLI='["/absolute/path/to/runtime", "/absolute/path/to/dsh-entry.js"]'
```

不要把 Token、Authorization header 等敏感信息写入命令、清单或日志。虽然运行时探测会避免回显 `DSH_CLI` 参数，仍应优先使用环境或凭据系统提供认证。

## 6. 清单与声明式命令

### `install <spec>`

向指定 Profile 的清单添加或覆盖一个别名：

```bash
# npm，建议固定明确版本
dshenv install @nanmicoder/dsh-agent-teams@0.1.21 --profile web

# 自定义别名
dshenv install @scope/example@1.2.3 --profile web --as example

# 本地目录；写入清单时会转换为绝对路径
dshenv install /absolute/path/to/plugin --profile web

# Git URL（替换为实际仓库和固定 ref）
dshenv install 'https://github.com/example/dsh-plugin-example.git#main' --profile web
```

支持的清单源码类型包括 `npm`、`git`、`local-link`、`local-file` 和 `in-box`。但命令行 `install` 目前直接识别 npm、Git 和本地路径三类输入。

Git 计划必须在 `lock.json` 中有确定的 commit；只有清单中的分支、ref 或未锁定 commit 不足以应用，计划会显示 `blocked`。通过 `capture`/`adopt` 接管已有、可确定 commit 的 Git 安装，可以生成对应锁记录。

### `enable` 与 `disable`

```bash
dshenv enable agent-teams --profile web
dshenv disable agent-teams --profile web
```

这两个命令只把清单中的 `enabled` 改为 `true` 或 `false`。如果实际状态不同，`plan` 会生成 `enable` 或 `disable`；当前 DSH CLI 适配器尚不支持执行它们，`apply` 会返回退出码 `4`，而不会假装成功。

### `remove`

```bash
dshenv remove agent-teams --profile web --yes
```

`remove` 只删除清单声明。若该插件在 `state.ownership` 中，随后的 `apply --yes` 会从 `bundles` 移除并调用 `dsh plugin remove`。没有所有权记录的实际插件会显示为 `unmanaged`，不会生成删除操作。当前 `--yes` 被命令接受，但 `remove` 本身没有交互确认，也不会立刻卸载。

### 当前 `apply` 支持矩阵

| 计划操作 | `apply` 是否执行 | 说明 |
| --- | --- | --- |
| `install` | 是 | 通过 DSH CLI 的插件添加操作执行 |
| `update` | 是 | 使用同一添加操作收敛到目标版本 |
| `enable` | 否 | 明确返回能力错误 |
| `disable` | 否 | 明确返回能力错误 |
| `remove` | 仅受管 | 无所有权则只标 unmanaged；有所有权则 `apply` 调用 `dsh plugin remove` |
| 配置补丁 | 否 | 当前会产生 `blocked` 计划 |

## 7. `plan`、`status` 与退出码

```bash
dshenv plan
dshenv status
dshenv --json status
```

- `plan` 展示逐项操作和未受管插件。
- `status` 汇总环境状态、Profile 数量和待执行操作数量。
- 全局参数 `--json` 可供脚本和 CI 使用。

退出码约定：

| 退出码 | 含义 |
| --- | --- |
| `0` | 命令成功；对 `plan/status` 表示没有可执行漂移 |
| `1` | 通用 CLI 或参数错误 |
| `2` | `plan/status` 发现 `install/update/enable/disable` 等有效漂移 |
| `3` | 清单、输入或目标文件校验失败 |
| `4` | DSH 能力、命令解析或操作类型不受支持 |
| `5` | 环境降级、存在 `blocked` 计划或运行时执行后未收敛 |

在 shell 脚本中应显式接受漂移退出码：

```bash
set +e
dshenv plan
code=$?
set -e

if [ "$code" -eq 0 ]; then
  echo "环境已同步"
elif [ "$code" -eq 2 ]; then
  echo "发现待应用变更"
else
  exit "$code"
fi
```

仅存在 `unmanaged` 插件时，计划没有删除操作，因此 `plan` 当前返回 `0`；请同时阅读输出中的未受管列表。

## 8. 捕获和接管现有环境

已有 DSH Profile 不需要重新安装，可以先捕获实际状态：

```bash
# 输出到终端，不修改管理文件
dshenv capture

# 只捕获 web Profile，并写入新的候选文件
dshenv capture --profile web --output ./web-candidate.yaml
```

`--output` 使用“仅创建”方式写文件，已有同名文件时拒绝覆盖。候选文件同时包含 `manifest`、`lock` 和警告，必须先人工审阅。

确认后接管：

```bash
dshenv adopt --from ./web-candidate.yaml --yes
```

`adopt` 会重新盘点实际环境并检查候选是否过期，然后合并清单、锁文件和所有权记录。当实际安装版本可以读取时，候选中的 npm 版本必须与其一致；插件已经消失或可读取的版本发生变化时会拒绝接管。

当前 `adopt` 接受 `--yes`，但没有交互确认流程，因此务必在执行前审阅候选文件。

`capture` 本身不会接管所有权，只有 `adopt` 会更新活动管理文件。

## 9. 管理本地和 Git 源码

`source` 子命令是源码目录辅助工具，不会自动把源码加入 `manifest.yaml`：

```bash
# 查看 Git 工作区状态；--json 时还会包含本地包摘要和内容 digest
dshenv source status /absolute/path/to/plugin
dshenv --json source status /absolute/path/to/plugin

# 克隆仓库
dshenv source clone https://example.invalid/plugin.git /absolute/path/to/plugin --ref main

# 只允许 fast-forward 更新
dshenv source pull /absolute/path/to/plugin origin/main
```

`source pull` 遇到未提交改动会拒绝更新，避免覆盖本地工作。完成源码准备后，仍需通过 `install` 或编辑并校验清单来声明插件。

## 10. 使用 `doctor` 排查运行时

```bash
dshenv doctor
dshenv --json doctor
dshenv \
  --harness-source /Users/costalong/code/dsh/deepseek-harness \
  doctor
```

`doctor` 会检查 DSH 版本、运行时发现能力、官方操作表面证据以及管理文件是否存在。

能力矩阵中的 `mutations=false` 或 `runtime.mutationsSupported=false` 表示通用、完整的环境写能力仍未开放；它不等于 `apply` 命令不存在。当前 `apply` 是一条范围更窄的 DSH CLI 适配路径，只执行插件 `install/update`。

`doctor` 默认拒绝未经验证的 DSH 版本。确需试验时可显式放行：

```bash
dshenv --allow-untested-dsh doctor
```

这只绕过 `doctor` 的版本白名单，不保证该版本与当前适配器兼容。当前 `apply` 尚未使用 `doctor` 的版本与能力矩阵作为前置门禁；真实执行前应先单独运行 `doctor` 并确认结果。

## 11. 卸载、清理与 purge

当前需要区分三件事：

1. 卸载 `dshenv` CLI：使用 `pnpm remove --global dsh-envctl`。
2. 从清单移除插件：使用 `dshenv remove <alias> --profile <name>`。
3. 从 DSH Profile 卸载受管插件：在上一步之后运行 `dshenv apply --yes`。没有所有权记录的插件会变成 `unmanaged`，需要用官方方式处理。

`dshenv rollback --yes` 只恢复 `envctl` 下的 `manifest.yaml` / `lock.json` / `state.json`，不会卸载或重装 Profile 里的包。`dshenv gc --yes` 只删除 `envctl/trash` 中超过 `--older-than`（默认 7 天）的条目。当前没有 `purge` 命令把资源移入 trash。不要为了重新初始化而直接删除整个 `$DSH_HOME`。

## 12. 安全注意事项

- 在任何真实变更前先执行 `plan` 和 `apply --dry-run`。
- `apply` 会获取 `$DSH_HOME/envctl/dshenv.lock` 独占锁，并在 `envctl/backups/` 备份当时已经存在的 `manifest.yaml`、`lock.json`、`state.json`。
- 当前失败补偿只覆盖恢复快照中原先存在的管理文件，不能恢复文件原本缺失的状态，也不保证撤销 DSH CLI 已经完成的 Profile 包变更；失败后必须重新运行 `status` 和 `plan`。
- `journal.jsonl` 记录操作开始、完成或回滚事件，但不是完整的 Profile 文件备份。
- 未在清单中的插件被视为 `unmanaged`，不会被静默删除。
- 本地链接和本地文件路径必须是绝对路径；只使用可信源码目录和规范的 npm 包名。
- Git 更新要求工作区干净，并只执行 fast-forward 合并。
- `lock.json` 是确定性输入；不要随意删除或伪造 Git commit、npm 解析版本。
- 不要在清单、锁文件、patch 配置、源码 `package.json`、终端命令或操作日志中保存明文密钥。`source status --json` 会输出源码包摘要，调用前应检查其中是否包含敏感字段。

## 13. 常见错误排查

### `Target file already exists`

原因：对已经初始化的目录再次执行了 `init`，或者 `capture --output` 指向已有文件。

处理：继续使用现有环境，先运行：

```bash
dshenv status
dshenv plan
```

需要全新演示环境时，改用新的 `DSH_HOME`，不要直接覆盖原管理文件：

```bash
DSH_HOME=/Users/costalong/code/dsh/dsh-demo-2 dshenv init
```

### `make` 把退出码 `2` 显示为错误

直接执行 `dshenv plan/status` 时，退出码 `2` 表示发现漂移。当前 `make demo-status` 只接受退出码 `0/2`；`demo-plan` 使用 Make 的忽略错误前缀，会忽略包括校验或降级错误在内的所有非零退出码，因此排错和 CI 应直接运行 `dshenv plan` 并检查退出码。

### `DSH CLI was not found`

确认下列方式至少有一种可用：

```bash
dshenv --harness-source /absolute/path/to/deepseek-harness doctor

export DSH_CLI=/absolute/path/to/dsh
dshenv doctor

command -v dsh
```

### `Apply operation 'enable'/'disable' is not supported`

这是当前能力边界，不是重试可以解决的瞬时错误。保留清单变更用于审阅，等待适配器支持，或使用与当前 DSH 版本匹配的官方操作后重新盘点。

### `Git source has no locked commit`

Git 源缺少 `lock.json` 中的确定 commit。不要让工具猜测 HEAD；先固定来源，并通过 `capture`/`adopt` 形成可验证的锁记录。

### `Apply execution finished but the environment still has pending operations`

DSH 子命令返回成功，但重新盘点仍发现漂移。查看 Profile 的 `package.json`、DSH 输出和：

```bash
dshenv status
dshenv plan
tail -n 20 "$DSH_HOME/envctl/logs/journal.jsonl"
```

该情况返回退出码 `5`，不会提交新的成功状态。

### `Environment lock is already held`

另一个 `apply` 可能仍在运行。先确认对应进程是否存在；不要在活动操作期间手工删除锁文件。对同一主机上已经退出的进程，工具会尝试识别并接管陈旧锁。

### `source pull` 拒绝脏工作区

先在目标仓库提交或暂存本地修改，再重新执行。工具不会自动丢弃未提交内容。
