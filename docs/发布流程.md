# 发布流程

版本号遵循语义化版本，唯一来源是 `package.json` 的 `version`（`dshenv --version` 读取它）。推送 `v<版本>` tag 后，`.github/workflows/release.yml` 自动完成发布。

## 步骤

1. 发布改动通过 PR 合入 `master`（`master` 受保护：必须走 PR，`check (22)`、`check (24)` 通过后才能合入），确认 `master` 上 CI 通过，本地切到最新的 `master` 且工作区干净。
2. 修改 `package.json` 的 `version`。
3. 在 `CHANGELOG.md` 顶部新增 `## <版本> - <YYYY-MM-DD>` 小节，写明新增、变更与修复。
4. 把 `README.md` 与 `docs/使用教程.md` 安装说明中的版本号（`@costa92/dshenv@<版本>` 与 `#v<版本>`）改为新版本。
5. 本地检查：

   ```bash
   pnpm typecheck && pnpm test && pnpm build
   node bin/dshenv.js --version   # 应输出新版本
   ```

6. 版本提交同样走 PR，合入后在 `master` 上打 tag：

   ```bash
   git switch -c release/v<版本>
   git commit -am "chore: release v<版本>"
   git push -u origin release/v<版本>
   gh pr create --fill && gh pr merge --merge --auto   # CI 通过后自动合入
   git switch master && git pull --ff-only
   git tag -a v<版本> -m "v<版本>"
   git push origin v<版本>
   ```

## Release 工作流做什么

1. tag 必须等于 `v` + `package.json` 的版本，否则失败。
2. 从 `CHANGELOG.md` 取出该版本小节作为 Release 说明，缺少该小节则失败。
3. 与 CI 相同的 `typecheck`、`test`、`build`。
4. `pnpm pack` 生成 `costa92-dshenv-<版本>.tgz`，把 npm 升级到 11.5.1 以上，通过 Trusted Publishing 把这份文件发布到 npm（`@costa92/dshenv`，公开，自动附带 provenance），再创建 GitHub Release 并附上同一文件。包内已含 `lib/`，安装时不需要构建。

任一步失败都不会创建 Release。修正后删除远端 tag（`git push origin :refs/tags/v<版本>`）与本地 tag，重新打 tag 推送。

## npm Trusted Publishing

npm 通过 GitHub Actions 的 OIDC 身份信任 `release.yml` 时不需要 token，并自动生成 provenance。要求 npm CLI ≥ 11.5.1、Node ≥ 22.14.0（工作流会先升级 npm）、工作流权限 `id-token: write`。

可信发布者尚未在 npmjs.com 登记成功（0.3.0 发布时 OIDC 换取凭证返回 `package not found`），因此发布步骤暂时设置 `NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}`：npm 先尝试 OIDC，失败时改用这个 token，`--provenance` 照常生成 provenance。登记成功后，发布日志里不再出现 `oidc Failed token exchange`，此时再去掉 `NODE_AUTH_TOKEN` 并按下面第 2 步收紧权限。

一次性配置（需要包的维护者登录 npmjs.com 操作）：

1. 打开 `@costa92/dshenv` 的 **Settings → Trusted Publisher**，选择 GitHub Actions，填写：Organization or user `costa92`，Repository `dshenv`，Workflow filename `release.yml`，Environment 留空。
2. 用这套配置成功发布一个版本后，再收紧权限：**Settings → Publishing access** 选择 “Require two-factor authentication and disallow tokens”，删除仓库 Secret（`gh secret delete NPM_TOKEN -R costa92/dshenv --app actions`），并在 npmjs.com 撤销原来的 Granular Access Token。

发布失败并提示 `ENEEDAUTH` 或 404 时，先检查上面四个字段是否与仓库、工作流文件名完全一致。

包名用 `@costa92` 作用域：npm 以「与 dotenv、osenv 过于相似」为由拒绝了无作用域的 `dshenv`。
