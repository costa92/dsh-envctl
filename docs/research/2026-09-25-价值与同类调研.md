# dshenv 价值、同类与优化调研

调研日期：2026-09-25。对象：本仓库已批准设计 `dshenv`（Environment-as-Code 层）。依据：设计规格、只读原型计划、DSH 官方插件管理器文档、公开同类仓库。

## 一句话结论

值得做，但只值得做「声明式环境层」，不值得再做一个插件 GUI / 市场 / 发行版。

官方 `dsh plugin` 和 `@deepseek-ai/dsh-plugin-manager` 已经覆盖「对当前 Profile 装、卸、开关」。社区里同类 GUI、备份、诊断、发行版很多。没有找到与 `dshenv` 同定位的公开项目：跨 Profile 的期望状态 + 锁文件 + plan/apply 漂移 + 配置块所有权 + Git/本地源码生命周期。

首个有价值交付不是 `apply`，而是只读的 `capture / status / plan / doctor`。写路径必须等官方能力表允许，并且只能走官方适配器。

## 当前项目是什么

`dshenv` 不替代官方管理器，不建设市场，不做成主观 DSH 发行版。它在官方能力之上加一层：

```text
清单（期望） + 锁（精确制品）
        ↓
   盘点实际状态
        ↓
   确定性 plan
        ↓
   仅修改已声明所有权的资源
```

验证对象是 Web Profile 与 `@nanmicoder/dsh-agent-teams`，实现不得含该插件特例。首版不改 DSH 源码、不管 Desktop 内嵌 Harness、不自动重启、不删共享数据。

仓库现状（已核实）：设计与只读原型计划已落地；`package.json` / 版本测试已出现但未入库；`src/` 与可执行 CLI 尚不存在；无 git remote。

## 能解决什么问题

DSH 的真实工作面被拆成多层，官方只保证「当前 Profile 的一次操作」，不保证「这台机器上的环境可复现」。

```text
bundles 顺序（package.json dsh.profile）
  + 依赖与 pnpm-lock
  + cordis.patch.yml（用户层，后写覆盖整行 config）
  + 主目录 patch / settings / 凭据
  + 本地 link / file / git spec
  + 兼容性豁免 compatibility.json
  + pnpm allowBuilds
```

这些层会被 CLI、Web 插件页、Agent 工具、手工编辑同时改。缺少一个可审阅的期望状态。

| 痛点 | 现状 | dshenv 对应能力 |
|---|---|---|
| 环境不可复现 | `dsh plugin update` 本质是 pnpm update，会漂到 latest；`npx @deepseek-ai/dsh` 每次拉新 runtime | 清单 + `lock.json`；普通 `apply` 用锁，只有 `update` 解析新版 |
| 多入口漂移 | GUI / Agent / CLI / 手改同一份 patch | `plan` 解释漂移；非受管只展示不协调 |
| 配置所有权不清 | 社区管理器常整文件重写 `cordis.patch.yml`；重复 `id` 会启动失败 | 只改 `# dshenv:begin/end` 标记块；`adopt` 才接管 |
| 本地开发无流程 | `link:` / `file:` / git 混用；脏工作树被自动 stash 会丢改动 | npm / 受管 Git / 外部本地三类来源；脏树拒绝危险操作 |
| 失败不可恢复 | 官方失败卸载可留部分变更；安装失败恢复 manifest/lock 但不清下载物 | 环境级操作日志、备份、补偿、`degraded` 阻断后续变更 |
| CI 无法断言 | 没有稳定退出码表达「有漂移 / 能力不支持」 | `--json` + 退出码 0/2/3/4/5 |
| 密钥泄漏 | 日志、计划、备份容易带上展开后的凭据 | 密钥只允许引用，输出脱敏 |
| 破坏性清理 | 插件数据、session、凭据与包混在 `$DSH_HOME` | `purge` 只移有独占证据的受管资源，外部源码永不删 |

官方已经解决的，本项目不要再做一遍：当前 Profile 的 install/enable/disable/remove、peer 兼容检查、`compatibility.json` 豁免、profile 写锁、安装失败回滚 `package.json` + `pnpm-lock.yaml`、HMR 热加载。

## 做了有哪些收获

对个人（costa 的 DSH 工作流）

- 把 Web Profile + AgentTeams + 本地插件源码收成可审阅清单，换机器或清 Profile 后能按锁重建。
- 开发插件时有固定流程：clone/link → plan → apply，而不是改 `package.json` 和 patch 碰运气。
- `doctor` / `plan --json` 可做 CI 门禁：环境漂了就失败，而不是跑起来才发现。

对工程能力

- 在高变更上游上做版本化适配器（当前设计已把 `0.1.7-rc.2` 标成 `mutations: false`）。
- 练习 Terraform 同类问题：期望/实际、所有权、漂移、补偿、原子写、锁、密钥。
- 把 DSH 组合模型（bundle 层 → profile patch → home patch）吃透，后续写插件不容易踩重复 id、host 包影子、allowBuilds。

对生态（有条件）

- 填补「声明式环境」空档，不与 GUI/市场抢入口。
- 若只读契约稳定，可向上游提 RFC：官方 `dsh plugin` 缺的是 plan/lock/ownership，不是又一个设置页。

不该期待的收获：用户增长、插件发现、替代官方管理器、做成 oh-my-dsh 那样的发行版。那些赛道已经挤满，且与已批准非目标冲突。

## 是否存在同样的项目

没有找到同定位的公开项目。相近但不相同的分成六类。

### 1. 官方：命令式 Profile 操作（底座，必须复用）

- [`@deepseek-ai/dsh-plugin-manager`](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/boot/plugin-manager/README.md)：当前 Profile 的装/卸/开关、兼容性、安装失败恢复、profile 写锁。导出 `./operations`。不管跨 Profile 期望状态，不提供环境级 lock/plan，不声明 patch 块所有权。
- `dsh plugin --profile <name> <pnpm args>`：pnpm 转发器 + bundle 列表调和。`update` 会漂。

`dshenv` 的正确关系是调用它，而不是重写它。设计已写明：重写基础管理逻辑或做市场必须重新评审。

### 2. 锁与钉死：最接近，但只做一半

| 项目 | 做什么 | 与 dshenv 的差 |
|---|---|---|
| [da-beda/dsh-lockstep](https://github.com/da-beda/dsh-lockstep) | 对比已审阅 lock 与 npm/GitHub，提出 pin bump；**不执行** `dsh plugin update` | 不管配置块、Git 工作树、本地源码、所有权、事务恢复；`apply --write` 只写 lock |
| 各 Profile 的 `pnpm-lock.yaml` | 依赖图锁定 | 每个 Profile 一份；不含 patch 所有权、enabled、来源策略 |

dsh-lockstep 的问题陈述与本项目重合：「RC 期插件以进程权限运行，默认漂到 latest 是错的」。可兼容，不可替代。

### 3. 备份 / 迁移 / 同步：搬家，不是收敛

| 项目 | 做什么 | 与 dshenv 的差 |
|---|---|---|
| [xiajiajun516/dsh-config-manager](https://github.com/xiajiajun516/dsh-config-manager)（约 115 star） | ZIP 导出/导入、预览、回滚、Git/WebDAV 同步、配置市场 | 明确不把 `$DSH_HOME/profiles/<name>` 的插件栈当可迁移一等公民 |
| [lordqyxz/dsh-config-sync](https://github.com/lordqyxz/dsh-config-sync) | 镜像 `~/.dsh` 到 iCloud 等 | 目录复制，无期望状态 |
| [limlnx523/dsh-plus-plus](https://github.com/limlnx523/dsh-plus-plus) | 审计、回归测试、`$DSH_HOME` 快照 | 运维控制面，不 apply 声明式环境 |

备份解决「把现状打包走」；dshenv 解决「现状该不该等于这份清单」。

### 4. 社区插件管理器：命令式 GUI，与官方抢同一层

公开仓库很多，能力高度同质：列出插件、启停、偶尔安装、偶尔导出导入。代表：

- [MAXeaglet/dsh-plugin-manager](https://github.com/MAXeaglet/dsh-plugin-manager)：独立 Tauri GUI + CLI，直接读写 Profile 文件
- [Retr67/dsh-plugin-manager](https://github.com/Retr67/dsh-plugin-manager)、[buhuikongpan/dsh-pluginmanager](https://github.com/buhuikongpan/dsh-pluginmanager)、[liqichen/dsh-plugin-manager](https://github.com/liqichen/dsh-plugin-manager)、[TAOxxx7/dsh-plugin-manager](https://github.com/TAOxxx7/dsh-plugin-manager)、[OSSKn4w7/dsh-plugin-manager](https://dshplugin.store/plugin/OSSKn4w7/dsh-plugin-manager)

它们解决「不要手改 YAML」。多数整段改 patch、无锁、无 plan、无非受管保护。和已批准非目标（无 GUI/市场）不冲突，也不构成替代。

### 5. 诊断：只读健康检查，可组合不可吞并

- [zoahdev/dsh-plugin-doctor](https://github.com/zoahdev/dsh-plugin-doctor)：manifest/patch、host 包影子、BOM、fresh-profile 安装
- [moonquake2004/dsh-doctor](https://github.com/moonquake2004/dsh-doctor)：重复 id、file: 损坏、双实例
- [jorinyang/dsh-doctor](https://github.com/jorinyang/dsh-doctor)：崩溃诊断与可逆修复

`dshenv doctor` 应探测环境与能力，不要复制这些检查的实现。发现影子包或重复 id 时，指向这些工具或复用其结果。

### 6. 发行版 / Overlay：与非目标相反

- [amplifthq/oh-my-dsh](https://github.com/amplifthq/oh-my-dsh)：策展 overlay，精确 pin + 完整性哈希，明确「不是 fork」
- [LaplaceYoung/oh-my-dsh](https://github.com/LaplaceYoung/oh-my-dsh)：能力库
- [zsagi1368/zDSH-Go](https://github.com/zsagi1368/zDSH-Go)：fork + 预装插件

设计已禁止做成主观发行版。可借鉴其「精确 pin、不改 node_modules、seam 破坏就停」的纪律，不要借鉴「我们替你选插件」。

设计文档还引用了 `cdllang/dsh-plugin-manager-plus` 与 `ggggggggggz/dsh-config`。本次公开检索未定位到对应仓库，不当作仍存活的竞品。

### 跨生态类比（方法来源，不是竞品）

| 类比 | 可借鉴 | 不要照搬 |
|---|---|---|
| Terraform | plan/apply、state、drift、退出码 | 远程 backend、provider 生态 |
| Nix profile / home-manager | 声明式用户环境 | 纯函数闭包、替换整个系统 |
| lazy.nvim lockfile | 跨机器钉 commit；dev 本地插件 | 启动时自动装最新（lazy 曾因此被抱怨） |
| chezmoi | 配置所有权与模板 | 不管包安装 |
| direnv / devenv | 项目级环境 | 不管 Harness Profile |

## 若继续做：优化建议

按影响排序。未改变已批准目标/非目标，只收紧怎么做。

### 1. 把只读原型当成第一个产品，而不是施工脚手架

`capture / status / plan / doctor` 在 `mutations: false` 的 `0.1.7-rc.2` 上就能独立产生价值：看清环境、导出候选清单、CI 里断言无漂移。`apply` 在官方写能力未纳入能力表前不要做。

这与现行计划一致，执行时不要提前写 Profile。

### 2. 缩小首个可变范围

建议可变阶段再拆：先 npm 精确版 + 单个 Web Profile + 受管 patch 块；Git 与外部本地源码放下一份计划。三类来源一次做完，失败模式会缠在一起（脏树、symlink、构建批准、外部目录不可删）。

### 3. 不要重建已有子系统

| 禁止重建 | 改为 |
|---|---|
| pnpm / 官方 installBundle | 版本化适配器调用 `./operations` |
| 插件市场、GitHub 搜索 | 非目标 |
| host 影子、重复 id、BOM 的深度诊断 | 调用或提示 dsh-plugin-doctor |
| `$DSH_HOME` ZIP 搬家 | 让位给 config-manager；本工具只保证清单可重建插件栈 |
| 安全审计 / 回归测试 | 让位给 dsh-plus-plus 一类控制面 |

### 4. 锁文件考虑与 dsh-lockstep 对齐，而不是另起一套无法互转的 JSON

不必依赖它。若本项目 `lock.json` 能导入/导出 `{ runtime, plugins: [{ id, spec }] }`，团队可以 lockstep 做「世界是否移动」，dshenv 做「本机是否等于锁」。两套完全不同的锁会让用户只保留一个。

### 5. 设计里的本机绝对路径改成示例

规格中的 `/Users/costalong/code/dsh/plugins` 与 `deepseek-harness` 是安装实例，不能当默认值写进 Schema。默认应为空或相对约定，由 `DSH_PLUGIN_SOURCE_HOME` / `--harness-source` / 清单显式给出。否则工具无法给别人用，测试也会绑死这台机器。

### 6. 骨架与计划已经漂移，落地前先对齐

| 项 | 计划 | 当前 `package.json` |
|---|---|---|
| Node | `^22.19.0 \|\| >=24` | `>=22.19.0` |
| Commander | 14.0.3 | ^13.1.0 |
| Zod | 4.6.5 | ^3.24.2 |
| YAML | 2.9.1 | ^2.7.0 |
| Execa | 10.0.0 | ^9.5.2 |
| Vitest | 4.1.8 | ^3.0.7 |
| tsdown | 0.22.2 | ^0.15.6 |

只读计划要求精确版本。现在是 caret 范围且主版本落后。实现任务 1 时应按计划钉死，而不是沿用当前草稿。

### 7. 能力表做成唯一写开关

`0.1.7-rc.2` 已规定：`discovery: true, mutations: false`。任何写适配器必须按 DSH 版本分派；未知版本退出码 4，不改环境。上游是 developer preview，按周破 seam 是基准情景，不是意外。

### 8. 配置所有权是真正的护城河，也是最大翻车点

社区管理器翻车几乎都在「重写整份 `cordis.patch.yml`」。`# dshenv:begin/end` + digest + 只改块内字节，必须有独立测试：非受管共存、ID 冲突、digest 漂移、`adopt` 展示精确 diff。这块做对了，项目才和 GUI 管理器不是同一个东西。

### 9. 密钥与 `--yes` 纪律不要松

`--yes` 不能推导兼容性豁免或 pnpm 构建批准。构建许可按包名显式批准。日志禁止展开环境变量。这是相对 GUI 工具的可信度来源。

### 10. 延期项维持延期

Base+Overlay、动态 HMR、Service DAG、GH Actions、容器、远程分发：设计已延期。 overlays 在所有权模型未证明前会把「谁拥有这一行」打乱。

## 风险

| 失败模式 | 缓解 |
|---|---|
| 官方很快把 plan/lock 收进 plugin-manager，本项目失去差异 | 只读契约保持薄；写路径只做适配器。若官方覆盖，项目可收缩为清单格式 + CI，或把适配器贡献回去 |
| DSH RC 每周改 operations / patch 语义，适配器失守 | 能力表 + 未知版本拒绝变更 + 固定验证版本 `0.1.7-rc.2` |
| 做成第三个插件管理 GUI | 已批准非目标；评审时看到市场/TUI/发行版就停 |
| `apply` 误删非受管或外部源码 | 无 adopt 记录不生成 remove；purge 路径/inode/symlink 执行前再校验；测试禁用真实 `~/.dsh` |
| 与 lockstep、config-manager 用户心智重叠 | README 用三句话划界：锁检查 / 搬家 / 声明式收敛 |
| 个人路径写进默认配置，工具无法迁移 | 见优化 5 |

## 建议路径

1. 按只读计划做完并全局 link：`init/capture/status/plan/doctor`。
2. 用临时 `DSH_HOME` 对本地 `deepseek-harness` 冒烟，确认报告 `0.1.7-rc.2` 且源码树无变更。
3. 用 `capture` 导出本机 Web Profile 候选，人工审阅后再谈 `adopt`。
4. 官方 `mutations` 仍为 false 时，停在只读。不要手写 Profile。
5. 写路径立项时再开三份后续计划：官方变更与 adopt、Git/本地源码、恢复与 purge。
